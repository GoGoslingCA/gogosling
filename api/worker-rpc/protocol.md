# Daemon ↔ Worker Protocol (worker-rpc)

**Protocol Version: `1`**. The daemon `gogoslingd` launches the Python worker process as a child process. Both sides exchange **line-delimited JSON-RPC 2.0** messages via the worker's **stdin / stdout** (one message per line, UTF-8, terminated by `\n`; raw newlines are not permitted within messages). stderr is used solely for logging.

Requests can be sent in both directions: daemon → worker is a "forward request", and worker → daemon is a "reverse request" (prefixed with `host.`). Both sides must be able to continue processing the other side's requests while waiting for their own outgoing requests to complete (full duplex).

## 1. Lifecycle

```
daemon                                  worker
  │── spawn ─────────────────────────────►│
  │── worker.hello {protocol_version} ───►│
  │◄── result {protocol_version, …} ──────│   Incompatible version: daemon sends worker.shutdown and errors out
  │── worker.ping / run.start / … ───────►│
  │◄── run.event notifications / host.* reverse requests ──│
  │── worker.shutdown (notification) ────►│   worker cancels in-flight runs and cleans up; daemon kills it on timeout
```

- Worker crashes or stdout closes: daemon marks all in-flight runs on that process as `failed` and restarts the process with backoff.
- Daemon exits: worker exits upon reading EOF.

## 2. Forward Requests (daemon → worker)

### `worker.hello`
```json
{"protocol_version": "1", "daemon_version": "0.1.0", "locale": "zh"}
```
Result:
```json
{"protocol_version": "1", "worker_version": "0.1.0", "python": "3.12.14", "capabilities": ["run", "cancel", "providers.openai_compatible"]}
```
If the worker does not support this major version, it returns error code `-32001` (see §5).

### `worker.ping` → `"pong"`

### `worker.info` → `{"version", "python", "pid"}`

### `worker.shutdown` (Notification, no id)
The worker cancels in-flight runs, waits for cancellation cleanup, flushes pending events, and exits with code 0. Shutdown does not wait for model tasks to finish successfully.

### `run.start`
```json
{
  "run_id": "01…", "session_id": "01…",
  "agent": {"id": "01…", "name": "Assistant", "system_prompt": "…", "autonomy": "ask_risky"},
  "provider": {"kind": "openai_compatible", "base_url": "https://…/v1", "api_key": "…", "model": "gpt-…"},
  "messages": [ Message… ],
  "tools": [ ToolSpec… ],
  "options": {"max_steps": 32, "temperature": 0.7, "max_output_tokens": 4096}
}
```
- The JSON shapes of `messages` and `tools` are identical to Go's `model.Message` / `model.ToolSpec` (`snake_case`).
- `messages` contains only session history, **excluding `system` role messages**; system prompts are passed exclusively via `agent.system_prompt`, and the worker constructs its own system message (if a `system` message is received, the worker should ignore it rather than injecting it again).
- `provider.api_key` appears only in this request and must not be recorded by the worker.
- When `provider.kind` is `openai_compatible`, `base_url` must be non-empty; the worker must not silently fall back to a default provider.
- The result returns `{"accepted": true}` immediately; progress is reported back via `run.event` notifications. Duplicate submission of the same `run_id` returns error `-32002`.

### `run.cancel`
`{"run_id": "01…"}` → `{"cancelled": true}`; the worker subsequently emits the `run.cancelled` event. Returns `{"cancelled": false}` for an unknown or already-finished `run_id`.

## 3. Notifications (worker → daemon)

### `run.event`
```json
{"run_id": "01…", "event": RunEvent}
```
The shape of `RunEvent` is identical to Go's `model.RunEvent`. Types and sequence of events the worker must emit:

1. `run.started`
2. Arbitrary number of: `text.delta` (incremental text), `reasoning.delta` (optional, incremental model thinking content, excluded from the final message), `tool.call.started` (model decides to call a tool, followed by sending the reverse request `host.tool.call`), `tool.call.completed` (with `tool_result`), `usage`
3. Exactly one terminal state: `run.completed` (with `message`: final assistant message containing all `parts`; with cumulative `usage`), `run.failed` (with `error`), `run.cancelled`

Usage metric convention: each `usage` event is **an increment of a single model call** (accumulated by the daemon), `run.completed.usage` is the **cumulative value** for the entire run; `cache_write_tokens` must be populated if reported by the provider. `tool.call.completed.tool_result.truncated` passes through the value returned by the daemon as-is.

`run.completed.message` emitted by the worker must be accepted by its own `run.start` parser (e.g., it must not produce a `tool_call` snippet with an empty `name`), otherwise the session history will reject all subsequent runs.

`approval.*` and `message.created` are generated by the daemon and are not sent by the worker.

### `log`
`{"level": "info|warn|error", "message": "…", "fields": {…}}` — Optional; written to logs by the daemon.

## 4. Reverse Requests (worker → daemon)

### `host.tool.call`
```json
{"run_id": "01…", "call": {"id": "call_1", "name": "read_file", "arguments": {"path": "notes.md"}}}
```
Result: `{"result": {"call_id": "call_1", "content": "…", "is_error": false, "truncated": false}}`.

The daemon performs permission evaluation here (which may involve waiting a long time for user approval), sandbox execution, and auditing. The worker must allow this request to wait for a long time (no short timeouts) while remaining responsive to `run.cancel` during the wait; when cancelled, the daemon terminates the reverse request with error `-32003`.

### `host.secret.get` (Reserved, not provided in the current version)

## 5. Error Codes

| Code | Meaning |
|---|---|
| -32700 / -32600 / -32601 / -32602 / -32603 | JSON-RPC Standard: Parse error, Invalid request, Method not found, Invalid params, Internal error |
| -32001 | Protocol version incompatible |
| -32002 | Duplicate run_id |
| -32003 | Request aborted because the run was cancelled |
| -32004 | Permission denied (`host.tool.call`), with `data.reason` serving as the model-facing explanation |
| -32005 | Provider invocation failed, with `data.provider_error` being the sanitized reason |

## 6. Worker Process Resolution

The daemon searches for the worker process command in the following order:

1. Environment variable `GOGOSLING_WORKER_CMD` (a command and arguments parsed using shell-style quoting, without variable expansion; backslashes are preserved on Windows; set to `uv run --project worker gogosling-worker` during development).
2. A bundled Python runtime, invoked with `-m gogosling_worker`. Relative to the daemon executable, Linux uses `../worker/bin/python`; macOS checks `../Resources/worker/bin/python` and then `../worker/bin/python`; Windows checks `../worker/Scripts/python.exe` and then `../worker/bin/python.exe`. These are lookup locations, not a guarantee that a runtime is present in every build.
3. If not found, the daemon starts normally but `engine` reports `unavailable`, and run requests return an `unavailable` error.

Environment variables upon worker startup: `GOGOSLING_PROTOCOL_VERSION=1`, `GOGOSLING_LOCALE`, `PYTHONUNBUFFERED=1`, `PYTHONIOENCODING=utf-8`. The daemon also forwards only the following allowlisted environment variables:
- Basic: `PATH`, `HOME`, `TMPDIR`, `TEMP`, `TMP`, `LANG`, `LC_ALL`; Windows location variables `SystemRoot`, `SystemDrive`, `ComSpec`, `PATHEXT`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA` (authoritative definition: `internal/config.ChildEnvAllowlist`)
- Proxy and certificate configuration (proxy URLs may contain credentials and must be redacted in logs): `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` and their lowercase forms, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`

Exit: Upon receiving `worker.shutdown` or stdin EOF, the worker must terminate with exit code 0 within 5 seconds, and must not crash due to daemon threads during interpreter shutdown (such as read threads blocked on stdin); the daemon logs non-zero exit codes as exceptions.
